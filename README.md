# 1C: Log Exporter (OneSLogExporter) v2.6.6

Высокопроизводительный инструмент и отказоустойчивая фоновая служба Windows на платформе **.NET 10 (C# 14)** для безаллокационного потокового разбора, фильтрации и непрерывного экспорта журналов платформы **1С:Предприятие 8.3 / 8.2**:
* **Технологический журнал (ТЖ)**: текстовые файлы `*.log` в каталогах процессов (`rphost_*`, `rmngr_*`, `ragent_*`).
* **Журнал регистрации (ЖР)**: классический текстовый формат (`*.lgp`, `1Cv8.lgf`, `*.lgx`) и современный формат SQLite (`1Cv8.lgd`).

## Архитектура: Direct-Stream vs TwoStage

OneSLogExporter поддерживает две гибкие архитектуры доставки данных:

### 1. Режим Direct-Stream (Zero-Disk Overhead, Рекомендуемый)
Пакеты распарсенных документов отправляются в целевые базы данных (**ClickHouse** и **Elasticsearch**) напрямую из оперативной памяти:

```
[Журналы 1С (*.lgp / *.lgd / *.log)]
       │
       ▼  Zero-Allocation парсинг батча в RAM
[Memory Batch (5 000 записей)]
       │
       ├───► [ClickHouse (HTTP POST Bulk)]      ──► 15 000 - 30 000 строк/сек
       ├───► [Elasticsearch / OpenSearch]
       │
       └───► (Опционально) [Фоновый FileDump]  ──► Резервный архив на диске
```
* **Экстремальная скорость**: Исключены двойные дисковые операции (запись на диск -> чтение с диска -> повторная десериализация). Скорость экспорта достигает максимума пропускной способности сети и СУБД.
* **Надежность**: Смещение в `state.json` фиксируется только после успешного подтверждения вставки от СУБД (`200 OK`). При сетевом сбое или падении БД исключение корректно прерывает сдвиг позиции, и пакет отправляется повторно без потерь.

### 2. Режим TwoStage (Классический двухэтапный буфер)
Сбор и отправка строго разделены на два независимых этапа (Stage 1 -> Stage 2):
```
[Журналы 1С] ──► [Парсинг 1С] ──► [Локальный NDJSON дамп] ──► [JsonLogTransporter] ──► [ClickHouse / Elastic]
```
Распарсенные данные сначала сохраняются на диск, а встроенный транспортер вычитывает их порциями. Полезен при работе в сетях с нестабильным каналом или при харвестинге сторонними агентами (Filebeat, Vector).

## Ключевые возможности и архитектура v2.3.0

* **Потоковый Zero-Leak разбор (Streaming Chunk Callback)**:
  - Парсеры `EventLogParser` и `TechLogParser` больше не удерживают в памяти гигантские списки `List<T>`. Парсинг транслирует события во внешние обработчики пачками по 5000 записей через `Func<List<T>, Task>`, после чего пачка немедленно сбрасывается на диск в `FileDumper`, а память очищается.
  - Потребление RAM остаётся строго стабильным (~150-300 МБ) даже при непрерывной обработке логов объемом сотни гигабайт.
* **Раздельные семафоры ввода-вывода (Split Locking in FileDumper)**:
  - Полное разделение очередей записи для Журнала Регистрации (`_eventLogLock`) и Технологического Журнала (`_techLogLock`). Исключены взаимные блокировки потоков сбора при интенсивной параллельной записи дампов.
* **Высокоточный потоковый ридер (FastLogLineReader)**:
  - Исключены погрешности буферизации `StreamReader.BaseStream.Position` при работе с многобайтовыми кодировками UTF-8 и разделителями CRLF.
  - Точное вычисление `CurrentLineStartOffset` гарантирует корректность инкрементальных смещений в `state.json` и исключает дублирование или пропуск строк.
* **Корректный трекинг инкрементов SQLite (.lgd)**:
  - Метод `StateTracker.HasFileGrown` отслеживает реальный физический размер `.lgd` файла на диске, предотвращая ложные срабатывания от сравнения байтов с целочисленным первичным ключом `rowID`.
* **Строгая фильтрация устаревшего ТЖ (MaxAgeHours)**:
  - Сервис автоматически отсекает каталоги и файлы технологического журнала, созданные ранее временного окна `MaxAgeHours` (`cutoffUtc = DateTime.UtcNow.AddHours(-maxAgeHours)`), исключая холостую перечитку старых архивных файлов.
* **Отказоустойчивость отправки в ClickHouse**:
  - При сетевых сбоях или тайм-аутах HTTP-запроса к ClickHouse исключение корректно пробрасывается вверх, блокируя преждевременный сдвиг смещения в `state.json` и защищая данные от потери при недоступности СУБД.
* **Многоядерный параллельный разбор чанков (Multi-core Chunk Parsing)**:
  - Автоматическое разделение гигантских файлов ЖР на независимые сегменты (чанки) с параллельной обработкой через `Parallel.ForEach` на всех ядрах CPU.
  - Увеличение скорости разбора тяжелых `.lgp` файлов в 5–10 раз с динамическим контролем балансировки скобок и границ строк.
* **Мгновенный предпросмотр с конца (High-speed Tail Preview)**:
  - Инвертированное позиционирование от конца файла (`Seek` от EOF) позволяет открыть последние события за миллисекунды, не вычитывая гигабайты предшествующей истории.
* **Режим «АРХИВ» (LoadArchive)**:
  - Режим мониторинга: при отключенном флаге служба/GUI начинает чтение строго с текущего конца файла (EOF), исключая многочасовое вычитывание старых логов.
  - При включенном флаге «АРХИВ» производится глубокое пакетное чтение всей накопленной ретроспективы.
* **Отложенная фоновая индексация (Deferred Indexing)**:
  - Построение поисковых индексов вынесено в фоновый воркер: интерфейс становится доступным для фильтрации и навигации мгновенно после загрузки первых пакетов данных.
* **Полнофункциональный режим «Все записи» по умолчанию**:
  - Оптимизированный виртуализированный `DataGrid` и сессионный кэш на SQLite WAL обеспечивают гладкую прокрутку сотен тысяч строк при минимальном потреблении оперативной памяти.
* **Полная потокобезопасность**:
  - Четкое разделение UI-потока (Dispatcher) и фоновых вычислительных задач исключает любые межпоточные конфликты.

## Особенности и механизмы парсинга

### 1. Парсинг Технологического Журнала (`TechLogParser`)
* **Zero-Allocation заголовки**: разбор структуры заголовка `MM:SS.micro-dur,EventName,Level` через `ReadOnlySpan<char>` с SIMD-поиском разделителей (`SearchValues`).
* **Точное время**: микросекунды из заголовка дополняются до 100-наносекундных тиков .NET (`DateTimeKind.Utc`).
* **Корректная обработка кавычек и многострочных блоков**: парсинг сложных экранированных параметров 1С (удвоенные одинарные кавычки `''` внутри значений `Context='...'` и `Sql='...'`).
* **Санитизация и нормализация**: символы перевода строк `\n` и `\r` заменяются/удаляются в значениях свойств, гарантируя строгий построчный формат NDJSON (одна запись — одна строка).
* **Защита от OOM**: лимит длины текстовых полей `MaxFieldLength = 64 КБ` с корректной пометкой усечения `[TRUNCATED]`.

### 2. Парсинг Журнала Регистрации (`EventLogParser` и `LgdParser`)
* **Текстовый формат (.lgp / 1Cv8.lgf)**:
  - Скобочный токенизатор без регулярных выражений с корректным подсчетом баланса вложенных скобок `{}` и экранированных кавычек `""`.
  - Поддержка составных метаданных, событий аутентификации и динамических словарей `1Cv8.lgf`.
  - Автоматическое связывание пользователей и рабочих станций через кэш сессий (когда 1С опускает реквизиты в промежуточных событиях).
  - **Бинарный поиск даты ($O(\log N)$)**: позиционирование к началу целевого диапазона времени в файлах размером 100+ ГБ за 25–30 шагов `Seek` без чтения лишних гигабайт.
* **Формат SQLite (1Cv8.lgd)**:
  - Неблокирующее подключение в режиме `Mode=ReadOnly`, `Cache=Shared`, `PRAGMA query_only = ON`, `PRAGMA synchronous = OFF`.
  - Динамическая интроспекция структуры колонок (`PRAGMA table_info(EventLog)`) для полной совместимости со всеми релизами платформы 8.3.
  - Инкрементальное чтение по возрастанию `rowID` (`WHERE rowID > @fromRowId ORDER BY rowID ASC LIMIT @limit`).
  - Очистка и санитизация строк от непечатных управляющих символов и BOM.

### 3. Пропуск повторных событий по id (`DeduplicateById`)
Id записи детерминирован: первые 16 байт SHA-256 от исходного текста события и его источника (для ТЖ — процесс, PID и час файла, для ЖР — каталог базы). Одно и то же событие при повторном чтении получает тот же id.

Параметры задаются отдельно для ЖР и ТЖ (секции `EventLog` и `TechLog`):

| Параметр | По умолчанию | Назначение |
|---|---|---|
| `DeduplicateById` | `false` | Событие с уже отправленным id не разбирается, не пишется в дамп и не отправляется в ClickHouse/Elastic. |
| `DeduplicationCapacity` | `500000` | Сколько последних id помнит фильтр. Каждый id занимает 8 байт в памяти и на диске. |

Ограничения, которые следуют из того, как считается id:
* Две полностью одинаковые записи (тот же текст, сеанс и та же секунда в ЖР, та же микросекунда в ТЖ) считаются одним событием, и вторая не отправляется.
* В id входит путь к каталогу базы или имя каталога процесса ТЖ. Если сменить `DirectoryPath` (например, с локального пути на UNC), id изменятся, и уже отправленные записи фильтр не узнает.

Фильтр хранится в `dedup_eventlog.bin` и `dedup_techlog.bin` рядом с файлом состояния. Id попадает в фильтр только после успешной отправки пачки, поэтому при сбое отправки данные не теряются. Позиция в файле фиксируется после каждой отправленной пачки.

ClickHouse дополнительно отбрасывает повтор целой пачки: у каждого INSERT есть `insert_deduplication_token`, а новые таблицы создаются с `non_replicated_deduplication_window = 1000`. Для таблиц, созданных до этой версии, выполните один раз:

```sql
ALTER TABLE <db>.techlog  MODIFY SETTING non_replicated_deduplication_window = 1000;
ALTER TABLE <db>.eventlog MODIFY SETTING non_replicated_deduplication_window = 1000;
```

После обновления id меняют формат (раньше в ТЖ использовался MD5, в ЖР — `GetHashCode`), поэтому старые и новые записи одного события не совпадут по id.

### 4. Схлопывание повторов ЖР (`CollapseRepeats`)
`DeduplicateById` убирает только повторное чтение одной и той же записи. Поток разных, но однотипных событий он не сокращает: например, фоновое задание пишет сотни «Данные. Изменение» по одному документу, и у всех одинаковый УИД метаданных.

Для такого случая есть схлопывание в секции `EventLog`:

| Параметр | По умолчанию | Назначение |
|---|---|---|
| `CollapseRepeats` | `false` | События с одинаковыми УИД метаданных, событием и пользователем в одном окне отправляются одной записью. |
| `CollapseWindowSeconds` | `60` | Размер окна в секундах. Окна выровнены по времени (12:00:00–12:00:59, 12:01:00–12:01:59 и т. д.). |

Остаётся первая запись окна, в поле `RepeatCount` записывается число событий, которые она заменяет. Сколько событий было на самом деле, считается как `sum(RepeatCount)`, а не `count()`. Записи без УИД метаданных (начало и конец сеанса, вход в систему) не схлопываются.

Что теряется: время, данные (ссылка на объект) и комментарий у всех событий окна, кроме первого. Схлопывание идёт внутри пачки, поэтому окно на границе двух пачек даёт две записи; сумма `RepeatCount` при этом остаётся точной.

Новые таблицы ClickHouse создаются с колонкой `RepeatCount`. В существующую таблицу её нужно добавить, иначе ClickHouse молча отбросит поле:

```sql
ALTER TABLE <db>.eventlog ADD COLUMN IF NOT EXISTS RepeatCount UInt32 DEFAULT 1;
```

## Ротация дампов и интеграция с Filebeat / Logstash

Для взаимодействия с внешними сборщиками логов (Filebeat, Logstash, Vector) файлы дампов организуются в кольцевой буфер слотов:
* ТЖ: `data_tglog_{N}.json` (слоты 1..30)
* ЖР: `data_evlog_{N}.json` (слоты 1..30)

> **Надежность смещений Filebeat**:
> При заполнении всех слотов утилита находит самый старый файл и **физически удаляет его** перед пересозданием (`File.Delete`). В Windows NTFS это гарантирует выдачу нового дескриптора (File ID), благодаря чему Filebeat корректно сбрасывает harvester и начинает чтение нового файла строго с нулевого байта, исключая рассинхронизацию смещений.

## Возможности GUI-клиента

* **Работа с файлами любого объема (100+ ГБ)**:
  - Локальный сессионный кэш на SQLite WAL (`%TEMP%\OneSLogExporter\session_*.db`).
  - Виртуализированный WPF DataGrid: плавная прокрутка миллионов строк с минимальным расходом RAM.
* **Фильтрация в один клик**:
  - Кнопки `[ ДА ]` (включить) и `[ НЕ ]` (исключить) по значениям ячеек.
  - Полнотекстовый поиск с префиксами (`user:`, `event:`, `app:`, `meta:`, `comment:`) и отрицанием (`!`, `-`).
  - Быстрые пресеты периодов («Сегодня», «Вчера», «3 дня», «7 дней», «30 дней») и произвольный интервал.
  - Сохранение и загрузка настроек фильтрации в профили JSON.
* **Экспорт результатов**:
  - Выгрузка отфильтрованных данных в Excel (`.xlsx`) с автоподбором ширины колонок.
  - Сохранение в формат JSON Lines (NDJSON) или в форматированный JSON (массив с отступами).
* **Открытие JSON-дампов**:
  - «ОБЗОР ▾» → «Выбрать файл JSON» на вкладках ЖР и ТЖ, либо перетаскивание файла в поле пути.
  - Читаются `*.json`, `*.jsonl`, `*.ndjson`: построчные, массивом, с отступами, с обёрткой вокруг массива записей. Файл разбирается потоком, целиком в память не загружается.
  - Имена полей — те же, что в выгрузке программы (`id`, `DateTime`, `Event` и остальные), с учётом регистра.
  - Выгрузка таблицы ClickHouse (`SELECT * FROM ... FORMAT JSONEachRow`) открывается так же. Если поля `DateTime` в строке нет, дата берётся из `Date`.
  - Служба произвольные JSON-файлы не открывает: она читает журналы 1С и собственные построчные дампы из каталога `FileDump`. Строка без `DateTime`, но с `Date`, в таком дампе тоже будет принята.
  - Прямая отгрузка выделенных строк в ClickHouse или Elasticsearch.

Служба регистрируется с системным именем `OneSLogExporter` и отображаемым именем **«1C: Log Exporter»**.

### 1. Настройка параметров
Отредактируйте `publish\Service\appsettings.json`:

```jsonc
{
  "Exporter": {
    "PollingIntervalSeconds": 60,       // Интервал опроса файлов (в секундах)
    "StateFilePath": "state.json",       // Файл сохранения позиций чтения

    // Локальный буфер JSON-дампов (NDJSON)
    "FileDump": {
      "TechLogEnabled": true,          // Локальный дамп ТЖ
      "EventLogEnabled": true,         // Локальный дамп ЖР
      "TechLogDirectoryPath": "C:/1C_Export/json_dump/techlog",
      "EventLogDirectoryPath": "C:/1C_Export/json_dump/eventlog",
      "RetainedFileCountLimit": 30,     // Хранить до 30 файлов в каталоге
      "MaxTotalSizeMb": 500            // Не более 500 МБ на каталог

    "EventLog": {
      "Enabled": true,
      "DirectStream": true,                  // true = прямая вставка из RAM в ClickHouse/Elastic (без задержек диска)
      "DirectoryPath": "C:/Logs/1C/reg_1541", // Каталог кластера (reg_1541) или логов конкретной базы
      "DatabaseName": "demo_db",             // Имя базы в кластере 1С (автопоиск GUID и словаря 1Cv8.lgf)

    },

    // Мониторинг Технологического Журнала (.log)
    "TechLog": {
      "Enabled": true,

      "IndexId": "prod",
      "MaxAgeHours": 24,
      "DeduplicateById": false               // true = не отправлять уже отправленные записи

    "ClickHouse": {

      "Database": "default",

      "Password": "",

      "TechLogTable": "techlog",
```

## Особенности работы с памятью

* **Workstation GC**: служба сконфигурирована в режиме Workstation Garbage Collection (`ServerGarbageCollection = false`, `RetainVM = false`). Память оперативно возвращается операционной системе (`VirtualFree`), рабочий набор удерживается в пределах 100–300 МБ даже при обработке пиковых нагрузок.
* **Исключение LOH-аллокаций**: размер промежуточных буферов сериализатора строго ограничен, куча больших объектов (Large Object Heap) не фрагментируется.
* **Intra-batch Rolling**: порционная нарезка файлов дампа предотвращает вылет по лимитам при залповых генерациях логов 1С.
* **FastStringPool**: пул интернирования строк исключает повторные аллокации повторяющихся идентификаторов событий, пользователей и метаданных.
